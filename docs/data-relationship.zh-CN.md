# 录音卡、手机与电脑的数据关系

[English](./data-relationship.md)

动手写小程序、App 或电脑端之前，先按本文对齐数据放在哪。本文描述 AI录音卡、录音卡、手机缓存和电脑档案之间的关系。帧格式见 [中文协议](./protocol.zh-CN.md) 与 [Protocol](./protocol.md)。连上录音卡的步骤见 [接入技能](./skill.zh-CN.md)。优先事项见 [路线图](./roadmap.zh-CN.md)。

手机用微信小程序还是独立 App，下面的关系相同。差别只在缓存容量和后台传输能力。

## 三端各是什么

| 端 | 角色 |
| --- | --- |
| 录音卡 | 采集源。保存卡内录音和文件列表 |
| 手机 | 缓存。保存尚未交给电脑的音频、列表元数据；也可先做云转写 |
| 电脑 | 档案。保存完整音频、语料正文、转写和可检索详情（权威副本） |

```text
录音卡  --BLE 协议-->  手机缓存  --应用同步-->  电脑档案
   |                                      ^
   +------------ BLE 协议（网页测试平台 / CLI）--+
```

两条链路互相独立：

- **卡 ↔ 手机、卡 ↔ 电脑**走公开 BLE 协议。电脑今天用 CLI 或 Web Bluetooth 测试平台直接读卡。
- **手机 ↔ 电脑**走应用自己的同步会话，不是录音卡协议帧。音频、语料、标题、客户都走这条链路。

手机可以只连着卡，也可以只连着电脑。

## 各端保存什么

| 数据 | 录音卡 | 手机 | 电脑 |
| --- | --- | --- | --- |
| 音频文件 | 卡内原始录音 | 待回传的源文件，或尚未清掉的缓存 | 完整音频，权威副本 |
| 列表 | 文件名、时间、大小 | 标题、时间、客户、音频同步、语料同步 | 可检索的完整条目 |
| 语料正文 / 转写 | 不保存 | 可先转写并缓存；电脑确认接收后可不常驻 | 权威副本；仅在「可跳过 ASR」条件满足时不重跑 |
| 客户、标题、同步状态 | 不保存 | 列表元数据 | 与音频、语料放在一起 |

同一条录音用卡上的文件名对齐（主名 / stem），并用**音频内容指纹**防止同名不同文件。用户修改的标题只存在于手机和电脑，不能拿标题回卡上查找。

## 谁转写

转写**不是** BLE 协议能力，手机或电脑都可以调用云 ASR（或其它引擎）。

| 场景 | 做法 |
| --- | --- |
| 手机先转写 | 手机生成语料 → 应用同步写入电脑 → 满足跳过条件则电脑不跑 ASR |
| 电脑先转写 | 电脑写入权威语料 → 手机按需拉取预览；手机不必再转写 |
| 两端都还没有 | 先争用转写租约，胜者转写一次；另一端只同步结果 |
| 需要重跑 | 仅用户明确触发（例如电脑 CLI `--force`） |

语料元数据应保留至少：`provider`、`transcribed_on`（`phone` / `pc`）、`audio_sha256`（或实现约定的等价指纹）。跳过 ASR、冲突与删除规则见下一节。

## 同步不变量

实现手机 ↔ 电脑同步时，遵守下列不变量。PC CLI（`qs668-transcribe.py`）已按第 3 条跳过：非空正文 + `audio_sha256` 一致；缺字段或指纹不符会重跑 ASR。手机同步落地后应对齐同一套条件。

### 1. 音频与语料分开确认

- 同步单元拆开：`audio_sync` 与 `corpus_sync`（例如 `none` / `pending` / `ok` / `failed`）。
- **音频已同步** ≠ **语料已同步**。列表与详情必须能分别展示，不能只显示一个「已同步」。
- 「整条录音对电脑归档完成」= 音频 `ok`，且（语料 `ok`，或用户明确选择「只要音频、暂不转写」）。

### 2. 用指纹绑定音频与语料

- 以卡上文件名 **stem** 做人类可读键；以音频 **内容指纹**（推荐 SHA-256，至少 size + 可靠校验和）防止同名碰撞。
- 语料必须带 `audio_sha256`（或等价字段），表示「这份正文对应哪份音频」。
- 电脑上若同 stem 的本地音频指纹与语料声明不一致：视为**过期语料**，默认不跳过 ASR，并提示用户选择重转或强制保留旧文。

### 3. 何时可跳过 ASR

同时满足才默认跳过（任一侧）：

1. 目标端已有同 stem 的语料文件；
2. 语料正文非空（不仅有 YAML / 标题）；
3. 语料中的 `audio_sha256` 与当前音频指纹一致（尚无音频文件时，可先同步语料，但标记「待音频校验」；音频到达后若不匹配则降级为过期）。

不满足时：告警或允许转写，不把坏语料 / 空语料当成权威。`--force` 或等价「用户确认重跑」可覆盖以上规则。

### 4. 转写租约（降低双扣费）

- 任意一端开始云转写前，先在同步会话（或双方可见的任务表）写入短时**转写租约**：`stem`、指纹、发起端、过期时间。
- 另一端看到有效租约则等待结果同步，不并行打 ASR。
- 租约过期或失败后，任一端可重新申请。租约不能 100% 消除离线并发，但应覆盖「两端同时在线」的常见窗口。

### 5. 冲突：默认不覆盖

- 电脑已有**非空**权威语料时，手机同步默认**不覆盖**。
- 覆盖必须用户确认（或 CLI `--force`）。
- 不要用「后写入墙钟时间更大」作为后台默认同步的唯一规则（时钟不可靠）。

### 6. 双通道（手机同步 vs 电脑直连卡）

- 手机应用同步与电脑 BLE / CLI 直导可能同时发生。
- 以**指纹**合并：同一指纹只保留一份音频；语料仍按第 3、5 条处理。
- 若电脑已从卡导入音频，手机再推同一指纹的语料：只补语料，不重复占空间。
- 若指纹不同却同 stem：视为冲突，保留两份或请用户挑选，禁止静默互相覆盖。

### 7. 删除本地缓存的前提

| 删除对象 | 允许删除的前提 |
| --- | --- |
| 手机源音频 | 电脑已确认音频完整（`audio_sync=ok`） |
| 手机语料缓存 | 电脑已确认语料落盘且非空（`corpus_sync=ok`），或用户不要语料 |
| 卡内录音 | 永不并进默认同步；必须另一次明确操作 |

任一确认失败时，保留手机本地对应副本，列表显示失败 / 重试，不得显示成「已删除」。

### 8. 格式与通道

- 手机写入电脑的语料应落在 `archive/corpus/<stem>.md`，front matter 字段与电脑 CLI 产出对齐（至少 `title`、`audio`、`provider`、`audio_sha256`、`transcribed_on`、`sync_status`）。
- 同步通道的鉴权与传输安全由应用自行负责，不在录音卡协议范围内；勿在同步明文里夹带 ASR 密钥。

## 电脑档案目录

电脑上的权威副本放在仓库里的 `archive/`。音频和语料分开放，用卡上文件名的主名对齐。

| 数据 | 目录 | 例子 |
| --- | --- | --- |
| 电脑音频 | `archive/audio/` | `archive/audio/note20260710-162938.wav` |
| 电脑语料 | `archive/corpus/` | `archive/corpus/note20260710-162938.md` |

这两个目录只留在本机。录音和语料不提交。目录里的 `.gitkeep` 用来保住空目录。对话接入时用 `tools/qs668-bringup.py` 把导入结果直接写进 `archive/audio/`。云转写用 `tools/qs668-transcribe.py`，配置见仓库根目录 `.env.example`，结果写入 `archive/corpus/`。手机同步来的语料也应落到同一路径、同一 stem，以便与「可跳过 ASR」规则对齐。

## 一份录音落在哪

| 阶段 | 卡内文件 | 手机音频 | audio_sync | 手机语料 | corpus_sync | 电脑音频 | 电脑语料 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 只在卡上 | 有 | 无 | none | 无 | none | 无 | 无 |
| 待回传 PC | 有 | 有 | pending | 无或有 | none / pending | 无 | 无 |
| 手机已转写，语料待同步 | 有 | 有或无 | 任意 | 有 | pending | 无或有 | 无 |
| 音频已同步，语料未齐 | 有 | 有或无 | ok | 无或有 | none / pending / failed | 完整 | 无或不完整 |
| 同步中 / 失败 | 有 | 有 | pending / failed | 可选 | pending / failed | 不完整 | 无或不完整 |
| 音书均已同步，缓存还在 | 有 | 有 | ok | 可选 | ok 或用户跳过语料 | 完整 | 有则完整 |
| 已同步，手机源文件已删 | 有 | 无 | ok | 可不常驻 | ok 或用户跳过 | 完整 | 有则完整 |
| 电脑直接从卡导入 | 有 | 无 | 不适用 | 无 | 不适用 | 完整 | 有则完整 |

实时音频还没保存成文件时，不进入上表。等它成为卡上或手机上的一条文件，再标「待回传 PC」。

## 手机列表状态

主状态仍按音频生命周期分档；**语料用 `corpus_sync` 附加标志**，详情里必须能看出「音频好了、语料还没有」。

| 状态 | 手机上有什么 | 点进详情 |
| --- | --- | --- |
| 待回传 PC | 源文件；语料可选 | 可播放预览；若已转写可先看本地语料，并提示尚未交给电脑 |
| 已同步，缓存还在 | 源文件；`audio_sync=ok`；语料按 `corpus_sync` | 可播缓存；若 `corpus_sync≠ok` 明确显示语料未同步或失败 |
| 已同步，仅元数据 | 无源文件；元数据 + 两个 sync 标志 | 无本地语料且电脑也没有时提示连接电脑；有电脑语料则可按需拉取 |
| 同步中 / 失败 | 源文件还在 | 分项显示音频 / 语料进度或重试；已转写正文不得显示成已丢弃 |

## 动手时的边界

- 组帧、文件导入和录音控制以协议文档为准。
- 客户、标题、同步状态、语料正文由手机和电脑的应用数据保存，不写回录音卡。
- 手机可以先转写；电脑仅在「可跳过 ASR」条件满足时不重跑。
- 默认同步不覆盖电脑已有非空语料；不因同步自动删卡。
- 小程序和 App 共用这一套状态，不各写一套生命周期。
